# AI 单插槽：MCP（取代内置对话）

> 2026-10 修订：本 ADR 原为"双插槽（内置对话 + MCP）"，内置对话已删除，改为 MCP 单插槽。
> 口径以现行 ADR 为准：接入传输见 ADR-0026（Streamable HTTP），样式颜色纪律见 ADR-0024。

AI 驱动全流程只保留一条落地路径：把 `packages/ai-tools` 中的工具定义（JSON Schema + 执行器）暴露为 MCP Server，供外部 agent（Claude Code、Cursor 等）驱动。应用自身不再调用任何模型端点，也不保存任何 API Key。

推理发生在用户已有的模型订阅或本地模型上，Sqraft 只做确定性执行与渲染反馈，不引入服务端，也不做模型供应商适配。

## 为什么删掉内置对话

- **浏览器里根本连不上主流接入点**：实测 `opencode.ai` 等端点的预检请求无 CORS 头，渲染进程直连必然失败（见 ADR-0009）。桌面壳虽然能绕过，但那条链路的收益远小于维护成本。
- **它是半成品第二插槽**：Provider 配置、密钥存储、会话历史、消息渲染各一套，占着侧栏一个 tab 和一份持久化，却只对"允许跨域的自建端点 + 本地 Ollama"可用。
- **真正的资产是工具层**：全部工具定义与执行器（清单以 `packages/ai-tools` 的 `tools` 表为真源，**不要在这里写死数量**）不依赖任何 UI，删掉对话面板对 MCP 零影响。

## Considered Options

- 双插槽（原方案）：内置对话 + MCP。已否决——CORS 使内置对话对目标用户基本不可用，且会话/密钥的维护成本无法摊薄。
- 只做内置对话：失去"在 agent 里直接指挥设计稿"的生态位，且必须自带模型接入与计费心智。
- 桌面壳里用系统 HTTP 修好内置对话：技术上可行（见 ADR-0009 的预判），但等于为一个体验更差的插槽重建密钥存储、会话历史与消息 UI，没有用户需求支撑。

## Consequences

- 应用内**没有任何密钥、没有任何模型请求**；"纯单机"不再需要解释"为什么还要连模型"。
- 新增能力必须同时进工具 schema 与 GUI——工具层仍然是能力清单的真源，不允许出现只有 AI 能做的操作。
- 样式颜色**优先**引用 Token，也允许直接给字面量（ADR-0024：设计系统由用户自建，新文件不预置 Token；本条原先的"字面量在工具层拒绝"已被 ADR-0024 取代）。
- 工具执行器与 GUI 命令走同一校验路径，杜绝"AI 特权操作"。
- MCP 需要宿主进程，这是桌面壳存在的第一个理由（见 ADR-0019）。
- 空掉了"普通用户第一体验"：没有外部 agent 的用户拿不到 AI。这是明确的取舍，不是遗漏。
